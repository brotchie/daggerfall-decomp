# XnGine's data as C (src/engine_data/)

The canonical engine (`src/engine/`, docs/xngine_canonical.md) is plain C, but it has no data
of its own: it declares the engine's globals and tables as `extern`s, and the test harness's
linker (`tools/xn_rc.py`, `tools/xn_cload.py`) resolves them to their addresses in the loaded
FALL.EXE. That is right for the harness, where the original game (object 1) reads the
engine's data at those addresses, and it stays so. A build of the engine outside FALL.EXE
(the SDL port) needs the data in C. `src/engine_data/` is that data: a separate source set
that only the standalone build compiles, shown equal to FALL.EXE's.

`tools/xn_datagen.py` makes and checks it:

| command | what |
|---|---|
| `inventory` | compiles `src/engine/` (Watcom C32 10.0a) and lists every symbol its objects reference and do not define -> `config/xngine_data.csv` |
| `gen` | the generated parts of the data module, from the inventory: `ddefs.c`, `dtable.c` |
| `link` | proof (a): the standalone link that refuses FALL.EXE's addresses |
| `check` | proof (b): the data, loaded and generated, against FALL.EXE's load image |
| `all` | the four in turn |

After a change to an engine header, run `tools/xn_datagen.py all`: the inventory follows the
headers, and the data module is regenerated from it.

## The inventory (config/xngine_data.csv)

Columns: `symbol`, `owner`, `kind`, `address` (FALL.EXE's preferred address), `size`,
`ctype` (the declaration the definition uses: the headers' type, with the size an array
declared `[]` gets), `init` (how the data module gives it its value), `filled_by` (the engine
function that fills it at run time), `refs` (the engine files that reference it, or the
pointer that reaches it), `declared` (header:line), `boundary` (the class of its bytes in
`config/xngine_boundary.csv`: visible, private, unobserved) and `evidence`.

How it is made:

- **References.** The objects of `src/engine/*.c` and `glue.asm`, compiled as `xn_rc.py build`
  compiles them; a symbol is listed when an object references it and none defines it (395).
- **Types and sizes.** The declarations are parsed from the headers and the .c files; the
  compiler measures every size (`sizeof` in a file that includes every header). Every
  declaration a .c file repeats is compiled against the headers' (33 of them): the compiler
  rejects one that disagrees.
- **Addresses** come from `config/names.csv` and `config/xngine_aliases.csv`; the owner from
  the address (object 2 is the engine's; object 1's game code below 0x9DA1C, the libraries
  above it, `config/regions.csv`; object 3 the game's data).
- **Kinds** from FALL.EXE's load image: all zero, or not; LE fixups inside a symbol are
  pointers (to the game's functions, or into object 2).
- **Extents** of arrays the headers declare without a size: up to the next named address, or
  the evidence in `SIZES` (`xn_render_span_rows`: 9001 nodes, the row heads and the span
  pool; `xn_shade_blend_tables`: 2, from docs/engine/structs.md; the ring tables: 29).

The engine's data is 346 symbols (463,170 bytes; the largest are the frame's pools). Two are
reached only through the engine's pointer tables (`xn_poly_ring_tables`, the polygon rings;
`xn_face_edge_slots`, the face edge tables) and one only by the game (`xn_cam_roll`); the data
module declares those three in `xndata.h`.

### Computed

By the data module (`dcompute.c`, `xn_data_compute`), each equal to FALL.EXE's byte for byte:

- `xn_sin_table`: round(sin(2 pi k / 2048) * 2^28) for k = 0..2559, from the first quadrant
  by the sine's symmetries (a series in double precision; no value is within 10^-4 of a
  half). Entry 1718 is the original's, one more than the rounding (Q-DATA-01). The cosine is
  the same table from 512.
- `xn_math_sqrt_table`: round(4 sqrt(i)) for i = 0..4095, at most 255 (integers only).
- `xn_tex_record_offsets`: 20 k.
- The polygon rings, `xn_poly_ring_a`/`_b` and `xn_poly_ring_tables`: for each clipper buffer,
  three lead entries, then ring n for n = 3..27 (the n vertex addresses three times, then
  vertex n) and ring 28's first 56; the walker reads ring n at -n..2n-1, the entries before a
  ring being the last of the one before. The asm's `ring_a` has 26 entries and its [26..28]
  are `ring_b`'s [0..2]: C gives each 29 and copies those three.
- `xn_face_edge_tables`/`xn_face_edge_slots`: an n-gon's point slot offsets 0, 8, ..,
  8(n - 1) for n = 3..24, each closed by the next table's first slot (0).

Not computed: `xn_math_asin_values`, whose rounding has no formula found (truncation, except 22
entries with fractions .950 to .998 rounded up while others to .994 are not): loaded.

By the engine at run time (zero in the image and in the data module; `filled_by`):
`xn_mem_init` (the reciprocals `xn_recip16_table`, `xn_recip32_table`, `xn_colour_fill_table`),
`xn_render_init` (`xn_squares_table`, `xn_tex_size_mask`, the `xn_render_recip_table` block),
`xn_cam_set_focal` (the camera's rays), `xn_rand_noise_init` (the noise), `xn_water_init` (the
water's jitter and rows), `xn_sky_init_stars` (the stars).

### Aliases: one storage, several names

The asm names parts of its tables and structs as globals of their own. A standalone build must
keep one storage, so the headers define those names as macros (`ctype` gives each):

| name | is | |
|---|---|---|
| `xn_cos_table` | `xn_sin_table + 512` | xngine.h: one table of 2560 entries (it was declared 2048) |
| `xn_math_asin_table` | `xn_math_asin_values + 512` | xmath.h: the table is centred (indexed -512..511); `xn_math_asin_values` (0x15D400) is a new name in xngine_aliases.csv |
| `xn_cam_dir_x_mid`, `_y_mid` | `xn_cam_dir_x_table + 512`, `_y_table + 384` | xspan.h |
| `xn_squares_table_mid` | `xn_squares_table + 4096` | xlight.h |
| `xn_cam_forward_x/_y/_z` | `xn_cam_rotation.m[2][0..2]` | xcam.h |
| `xn_pick_view_x/_y`, `pick_distance`, `xn_scratch_vec_b`, `xn_pick_flat_x/_y/_z` | `xn_scratch_vecs.a.x`... | xpipe.h (Q-MODEL-03 shares it) |
| `xn_world_nature_archive`, `_ground_archive` | `xn_world_cell_header.nature_archive`, `.ground_archive` | xworld.h |

In the harness the macros address the same bytes as the names did (each resolves to the same
address in FALL.EXE).

Three overlaps of the asm's layout stay separate in C, each harmless: the last 13 of
`spell_effect_handlers`' 64 entries are `xn_kludge_menu_handlers` (read-only tables: both
copies name the same functions); `xn_poly_vertex_buf_b`'s 32nd vertex would be
`xn_poly_ring_a`'s first 3 entries (a clipped face has at most 30 vertices: 24 points, and one
more for each of the 6 planes); `xn_poly_ring_a`'s last 3 are `ring_b`'s first (above).

### The header fixes

`src/engine` changed only in declarations (and two casts that go with one):

- 40 declarations of engine data that only .c files had moved into the module's header:
  xflat.h (the flat sort list and counts, matrices, blend tables, `xn_pick_skip_flats`),
  xmodel.h (the model queue, matrices, messages), xtex.h (the archives, heap, unpack buffer,
  path, messages), xdraw.h (`xn_cel_row_buffer`, `xn_paperdoll_background`,
  `xn_draw_shade_row`), xmath.h (`xn_collide_normal`), xpipe.h (`xn_cam_pitch`).
- The aliases above.
- Two disagreements: flat.c declared `xn_fog_step` `s32` and `xn_fog_table_last` `s32`
  (xshade.h: `u32`, `u8 *`): flat.c includes xshade.h now. vid.c declared
  `int dpmi_lock_region(int, int)` and xsys.h `s32 dpmi_lock_region(void *, u32)`: xsys.h
  has the game's own prototype now (`int (int address, int size)`, src/lifted/int.c), and
  sys.c's two calls cast to `int`. Likewise `dpmi_unlock_region`.
- xhelmet.h includes xpipe.h (the pick's scratch names).

## The data module (src/engine_data/)

| file | |
|---|---|
| `xndata.h` | the interface: `xn_data_object2`, `xn_data_load`, `xn_data_compute`, the loader's table type |
| `ddefs.c` | generated: the 346 definitions, grouped by header, each with its address in FALL.EXE and how it gets its value; the C initializers; the declarations of the functions the code-address tables name. It includes every engine header, so the compiler checks each definition against every declaration |
| `dtable.c` | generated: the 50 initial symbols' storage, address and size (`xn_data_items`) |
| `dload.c` | `xn_data_object2` (object 2's load image from FALL.EXE's bytes: the LE header, the object table, the page map) and `xn_data_load` |
| `dcompute.c` | `xn_data_compute`: the generators |

No game bytes are in the repository: the definitions carry names, types, sizes and addresses;
the initializers are scalar defaults (each shown equal to the image) and function names; the
generators are formulas. Strings and tables come from the user's FALL.EXE at start-up.

### How the port loads the data

```c
u8 *exe = /* the whole of the user's FALL.EXE 1.07.213 */;
static u8 object2[XN_DATA_OBJECT2_SIZE];

if (!xn_data_object2(exe, exe_size, object2))
    /* not FALL.EXE 1.07.213 (object 2 is 0xA1568 bytes at 0xC0000) */;
xn_data_load(object2);          /* the 50 initial symbols: 6,909 bytes */
xn_data_compute();              /* the sine, the square roots, the rings, the edge tables */
/* then the game: its start-up calls the engine's inits (xn_mem_init, xn_render_init...) */
```

`xn_data_load` takes object 2's image as the file holds it or relocated: no loaded symbol
holds an address (the inventory checks it; the pointer tables are initializers).

## The proofs

**(a) The standalone link** (`xn_datagen.py link`): the 50 objects of `src/engine` (49 C files
and glue.asm) and the 4 of `src/engine_data`, compiled with Watcom 10.0a in one DOSBox-X
session (`wcc10.compile_many`, the harness's flags), linked by `xn_cload.link` at 0x20000000
with a resolver that never consults FALL.EXE: it gives a stub to the inventory's game and
runtime symbols and refuses everything else. Result: the data module defines all 346 engine
symbols; 122 symbols are left outside, all the game's or the runtime's (86 game functions,
14 game data, 8 libraries, 8 entries, 4 labels) and 2 Watcom floating-point symbols
(`__8087`, `__init_387_emulator`) that dcompute.c's sine declares and no fixup uses; nothing
refused, nothing unresolved, nothing the data module defines outside the inventory. Hardware
addresses are constants in the code (below), not symbols. Image 626,832 bytes, 120 stubs
(`build/xn_canon/data/standalone.pkl`).

**(b) Data equality** (`xn_datagen.py check`): a bare 32-bit machine (Unicorn, no game, no
DOS) loads the standalone image; the C's `xn_data_object2` reads FALL.EXE's bytes (equal to
`le.py`'s object 2), then `xn_data_load` and `xn_data_compute` run. Every engine symbol's bytes
are compared with FALL.EXE's load image at its address: pointer fields by what they point at
(FALL.EXE's fixup target and the C value, each as symbol + offset). **346 of 346 equal.** The
only bytes excused are 56 of `xn_poly_ring_tables`: the asm's padding after each ring block
(TASM's filler DB87DB87h, 7 entries each), which the walker never reads; C has zeros.

Then the tables the engine fills at run time, after running those inits in both worlds: the C's
`xn_mem_init`, `xn_rand_noise_init`, `xn_render_init` in the bare machine (DPMI and DOS calls
succeed, the allocator gives heap blocks), against the original game's after its boot (the
snapshot `build/emu/snap/save_blades.snap`); the camera's rays and scales after
`xn_cam_set_view_window` and `xn_cam_set_focal` with the snapshot's view; the water's and the
stars' tables after `xn_water_init` and `xn_sky_init_stars` from the seed the original's ran
from (found by a model of `xn_rand_next`: 192 and 1; the C then runs from it). **28 of 28
equal**: the reciprocals, the fill table, the noise and its fade, the squares, the texture
size masks, the 65,536 depth reciprocals, the camera's rays and 12 scale values, the water's
four tables, the stars and their colours (`build/xn_canon/data/check.json`).

**(c) The harness unchanged** (the header fixes in, run with
`XN_RC_OUT=build/xn_canon/data/rc`): `tools/xn_rc.py build` compiles and routes as before (no
route problem); `test --corpus -j 4`: **8,880 / 8,880 records** (643 / 643 functions; the
corpus has grown since part 2's 8,794); `test --boundary -j 4`: **2,819 / 2,819** game-called
records, 178 / 178 entries; `scenarios -j 4`: **1,675 / 1,675 frames identical** over 39
scenarios. `tools/build-and-verify.sh`: BUILD OK (FALL.EXE byte-identical; the matching build
does not see src/engine or src/engine_data).

## What a port must provide

- **FALL.EXE 1.07.213** at start-up: the 50 initial symbols' bytes.
- **The game's symbols** (from its own C, src/lifted and src/hand): the 86 functions and 14
  data of the inventory. The engine declares six of the functions itself
  (`u32 fatal_error(const char *)`, `int sound_timer_add(void (*)(void), int)`,
  `void sound_timer_remove(int)`, `void mem_check_heap(s32)`, `int dpmi_lock_region(int,
  int)`, `int dpmi_unlock_region(int, int)`); ddefs.c declares the 80 the tables name with
  their table's type.
- **The game's names for the engine's data.** The game references 108 object-2 addresses
  (1,723 sites): 3 functions it holds as pointers, and 105 data, all inside the data module's
  symbols. 39 of those are inside a symbol, not at its start, so the game's C must name them
  as elements and fields: `key_down[k]` (22 keys: `key_down_esc` is `key_down[1]`...), the
  joystick state `xn_joy` (11 fields: `joystick_x`, `joystick_y`, the buttons...),
  `pick_distance` (`xn_scratch_vecs.a.z`), `xn_cos_table`, `xn_shade_translucent_table`
  (`xn_shade_blend_tables[1]`), the cell header's two archives and `xn_anim_ticks`' high word.
- **The runtime**: an allocator in place of FALL.EXE's (`func_000A10A8`/`func_000A117E`),
  `exit`, `filelength`, the protected-mode vectors (`_dos_getvect`/setvect), the SOS sample
  calls (the VID player's sound); the interrupt entries, which call the C handlers
  (`xn_kbd_int9_handler`, `xn_joy_timer_isr`, `xn_sys_crit_error_handler`,
  `xn_sys_divide_error_handler`, `xn_serial_irq_com1`; the serial table's COM2-4 entries are
  the asm's copies of COM1's handler, which have no C: nothing installs them, the game opens
  COM1 only); the 4 code labels only bound memory locks (a port without DPMI ignores them).
- **The platform layer**: xdos.h (DOS's file services, the 'DOS:' messages, int 21h), xpc.h
  (DPMI, the BIOS keyboard, the PS/2 mouse rate, the mouse driver, int 2Fh, the vectors), the
  ports (`xn_inb`/`xn_outb`: the PIC, the PIT, the keyboard, the joystick, the palette, the
  retrace, COM1) and glue.asm's register calls (`xn_int10`...`xn_int33`) under them: pc.c
  and dos.c are where an SDL port puts its own services.
- **Hardware** (absolute addresses in the C): VGA memory at 0xA0000 (gfx.c's `VGA_MEMORY`;
  `screen_buffer` and `xn_gfx_buffer_base` start there until `xn_gfx_set_mode` sets a back
  buffer), the BIOS tick count (0x46C) and keyboard flags (0x417), the zero page (0..3FFh:
  `xn_sys_zero_page_save`/`_check`), and two quirks' addresses: linear 0Ch (Q-ANIM-01) and
  40006Ch (Q-RAND-01).

## Left

- `xn_math_asin_values` is loaded, not generated: no formula reproduces its rounding.
- The game's prototypes as the engine declares them differ from the lifted game C's in places
  (`fatal_error` returns `u32` here, `void` there): a port that compiles both together picks
  one.
- The data module is not part of the harness's build: a header change that the inventory does
  not follow shows up only in `xn_datagen.py all` (the link or the compile of ddefs.c fails).
